# 1. Project Overview

Project Name: AirCue

AirCue is a gesture-based presentation navigation system designed primarily for solo presenters.

It allows users to control presentation slides, navigate presentation content, operate a pointer, click and scroll using predefined hand gestures without physically interacting with their keyboard or mouse.

## Problem Statement

During solo presentations, project pitches, academic demonstrations, and professional presentations, presenters often struggle to manage their presentation while simultaneously explaining their ideas.

They must divide their attention between:
- Explaining their content.
- Navigating presentation slides.
- Operating the presentation pointer.
- Managing their laptop or presentation controls.
- Maintaining engagement with the audience.

AirCue aims to bridge this gap by providing a hands-free presentation interaction system.

## Core Objective

Build a lightweight, reliable, hardware-adaptive gesture recognition and presentation navigation system.

Its primary engineering priorities are:

1. Low end-to-end interaction latency.
2. Reliable gesture recognition.
3. Minimal false-positive gesture activations.
4. Stable hand tracking.
5. Efficient CPU and RAM utilization.
6. Hardware-adaptive execution.
7. GPU acceleration when demonstrably beneficial.
8. Predictable application behavior.
9. Reliable presentation software integration.

Do not optimize FPS at the expense of latency, responsiveness, or recognition reliability.

# 3. Gesture System Requirements

Formalize the following gesture vocabulary.

| Gesture | Action |
|---|---|
| Open palm + clockwise wrist rotation | Next slide |
| Open palm + counterclockwise wrist rotation | Previous slide |
| Closed fist | Pause tracking |
| Thumbs-up | Resume tracking |
| Pinch gesture | Toggle pointer mode |
| Index finger + thumb configuration | Pointer navigation |
| Pinch and release | Single click |
| Two intentional pinch actions within a defined interval | Double click |
| Peace sign | Scroll mode |
| Shaka gesture | Initiate exit process |

## Gesture Recognition Requirements

Every gesture must be:
- Recognized using appropriate landmark and motion features.
- Validated across multiple observations or a suitable temporal window.
- Resistant to accidental activation.
- Context-sensitive.
- Compatible with the current application state.
- Protected by suitable debounce and cooldown mechanisms.

Static gestures and dynamic gestures must be handled appropriately.

Do not treat every detected hand configuration as an immediate command.

## Gesture-Specific Requirements

### Slide Navigation
- Detect wrist orientation changes.
- Determine rotation direction.
- Establish a neutral starting position.
- Support configurable angular activation thresholds.
- Prevent repeated activation caused by tracking jitter.
- Support deliberate continuous rotation as an optional extension.

### Continuous Rotation
Use the existing open-palm rotation gesture.

Do not introduce another hand gesture unnecessarily.

Define:
- Activation threshold.
- Repeat interval.
- Rotation direction.
- Neutral-position release condition.
- Maximum repeat frequency.
- Cooldown behavior.

### Pause and Resume
- Fist pauses normal gesture processing.
- Thumbs-up resumes normal tracking.
- Resume detection must remain available while paused.
- Pause and resume must not accidentally trigger presentation actions.

### Pointer Mode
- Support normalized hand-coordinate mapping.
- Support different display resolutions.
- Minimize cursor jitter.
- Avoid excessive smoothing.
- Provide configurable pointer sensitivity.
- Maintain stable coordinate mapping.

### Clicking
- Define reliable pinch detection.
- Differentiate single and double clicks.
- Prevent repeated clicks from one continuous pinch.
- Define an appropriate double-click recognition interval.

### Scrolling
- Peace sign activates scrolling.
- Define scroll direction and speed mapping.
- Prevent unintended continuous scrolling.
- Scrolling must only be available in valid operating states.

### Exit
- Shaka gesture initiates an intentional exit process.
- Require a deliberate hold or confirmation.
- Never terminate the application because of a single uncertain recognition event.
- Provide a safe keyboard fallback.

# 4. Architecture Requirements

Analyze the existing architecture before proposing modifications.

The proposal should formalize clear separation between:

1. Camera Capture Layer
2. Frame Processing Layer
3. Hand Detection and Tracking Layer
4. Landmark Feature Extraction Layer
5. Gesture Recognition Layer
6. Temporal Validation Layer
7. State Management Layer
8. Command Management Layer
9. Presentation Action Adapter
10. Performance Monitoring Layer

The gesture recognition system must not directly execute PowerPoint commands.

Instead, recognized gestures should generate validated semantic events.

Example:

FIST_DETECTED → STATE_VALIDATION → PAUSE_TRACKING

The command manager must validate whether a command is allowed in the current state before execution.

Keep the architecture modular and replaceable.

Avoid unnecessary abstractions and excessive complexity.

## Reliability Targets

| Metric | Target |
|---|---:|
| Intended gesture recognition | At least 98% |
| False command activations | At most 1 per 30 minutes |

| Pointer availability during valid visibility | At least 95% |
